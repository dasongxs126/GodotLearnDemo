## 一、已定的两个基准数字

像素风**不按 1920×1080 画**，而是按一个低分辨率画、再整数倍放大（否则像素会被拉花）。
以下两个数字**定了就不再改**——改了等于所有资产重画。

| 项 | 决定 | 说明 |
| --- | --- | --- |
| **内部渲染分辨率** | **640×360** | 16:9；1920÷640 = 3，整数倍放大到 1920×1080 |
| **等距格尺寸** | **32×16**（菱形） | 角色精灵 **64×96**，脚踩格子中心 |

（2026-10-01 确认。备选方案曾为 480×270 + 32×16、960×540 + 48×24，未采用。）

> 这两个数字**箱庭探索与战斗共用**（见上一节的确认）。

### 已实测修正：角色精灵 32×48 → **64×96**

原文档建议"角色精灵约 32×48"。**这个数字是拍脑袋写的，实测站不住**，2026-10-01 已推翻。

做法：拿同一张 AI 原图（1024×1024）分别缩到 32×48 / 48×72 / 64×96，各自用 NEAREST 与 LANCZOS
放大 8 倍并排对比（`tools/compare_scale.py` → `tmp_preview/scale_compare_*.png`）。结论：

| 尺寸 | 可辨识度 |
| --- | --- |
| 32×48 | ❌ 只剩一团轮廓，认不出是狼人还是石头 |
| 48×72 | ⚠️ 勉强，能看出是个人形，看不出种族与装备 |
| **64×96** | ✅ **能看清**：狼头、深色战术服、青色发光纹路 |

**原因不是"缩得不够小"，而是源图类型不同**：32×48 是**真像素画**的合理尺寸（画家直接在
32×48 画布上逐像素点出来），而 AI 出的是 1024px 插画，缩到 32×48 等于"高分辨率缩略图"，
细节全部塌掉。**两者不是一回事**（遗留问题见 §九）。

同时修掉一个处理脚本的 bug：缩小大图**必须用 LANCZOS（面积平均）**，
原脚本用 NEAREST 相当于每 12 个像素抽 1 个，出来是噪点。

### 32×16 格 + 64×96 角色 = 角色占 2 格宽，这是**允许的**

64px 宽的精灵站在 32px 宽的格子上，横向会超出 1 格。**这不是错误**——
经典等距 SRPG（如《最终幻想战略版》）的精灵同样会超出脚下那一格：

- **站位只由脚底那个格点决定**，精灵可以往上、往两侧"溢出"；
- 溢出是**视觉厚度**的来源，强行把角色压进 1 格反而会显得又扁又小；
- 但要记住一条**布局约束**：**同排相邻单位至少间隔 2 格（64px）**，
  否则 64px 宽的精灵会互相压住 50%，糊成一堵墙（`tools/mock_battle.py` 踩过）。

### 已澄清：箱庭探索也用等距 ✅

**箱庭（探索/城市）与战斗同为等距视角**（2026-10-01 确认）。这条确认带来三个好处：

1. **视觉统一**——玩家进出战斗不会有"换了个游戏"的割裂感；
2. **素材可复用**——地面 tile、角色精灵在探索与战斗之间共享，**实际资产量比"两套视角"少一半**；
3. **规格只需定一套**——等距格尺寸定一次，两边都用。

> 推论：**角色精灵建议做成能在两个场景通用的规格**（同一朝向、同一脚底锚点），
> 不要为了战斗单独画一套。命名与目录也应从一开始就共用。

## 二、核心建议：不要一上来做逐帧动画

**推荐路线：静态精灵 + 代码变换 + 特效叠加。**

- 每个角色**先只出 1 张待机精灵**，演出由代码做：位移、缩放、翻转、闪白、抖动；
- 进攻、受击、阵亡都是**同一张精灵**的不同变换，再叠一层特效；
- 成本比逐帧动画**低一个数量级**。

理由：这一阶段要解决的是「**看得出这是个人、分得清是谁**」，不是「动作流畅」。
逐帧动画等玩法定型后再补，那时才知道哪些动作值得投入。

> 补充：规格书里 3v3 是**站桩对打**（只有站位编号 1/2/3，没有走位），
> 所以**每个角色只需要 1 个朝向**（面向敌方），不需要做 8 方向行走图。

#### 关于 tile 为什么要两张（2026-10-01 实测）

等距菱形**不要交给 AI 画**——32×16 的菱形是纯几何图形，AI 出的是一团灰白块，
边缘还带深色描边，根本不能用。**直接程序生成**：每行半宽 = `(1 - |y - 中心| / 半高) × 半宽`，
两行代码就拼出标准 2:1 菱形（见 `tools/process_art.py` → `_diamond()`）。

两张的用途不同：

| tile | 不透明度 | 用途 |
| --- | --- | --- |
| `tiles/ground.png` | **不透明** | 箱庭地形。要能盖住底下的东西，是"地"本身 |
| `tiles/grid.png` | **半透明青色** | 战斗场地。是"系统投影出的作战网格"，不是地 |

**战斗场地不能用不透明砖**：铺满会把背景广场盖成一张地垫，把背景的戏全抢了。
改成半透明青色后，正好和背景里已有的青色全息线接上，读起来是战术投影（见 `tmp_preview/mock_battle.png`）。

## 四、规格与命名

### 文件规格

- 格式：**PNG-32（带 alpha 通道）**。Godot 直接导入，不需要 TGA / PSD。
- **不要预乘 alpha**；**不要自带阴影**（影子单独出，否则和地面打架）。
- **不要做抗锯齿 / 半透明描边**——像素风要求边缘干净；
  导入时纹理过滤设为 **Nearest**（`TextureFilter = Nearest`），否则放大后会糊。
- 统一朝向：全部**朝右下**（面向敌方一侧），需要反向时由代码水平翻转。
- 命名：
  - `res://assets/characters/<角色id>/idle.png`
  - `res://assets/tiles/<用途>.png`
  - `res://assets/fx/<用途>.png`
  - `res://assets/ui/<用途>.png`

### 尺寸参考（按 640×360 + 32×16 菱形格）

| 元素 | 建议尺寸 |
| --- | --- |
| 角色待机精灵 | **64×96**（脚踩格子中心，头顶留演出空间；**32×48 实测不可辨识**，见 §一） |
| 角色影子 | 24×12（椭圆，半透明黑 α≈90） |
| 等距地面 tile | 32×16（程序生成，不要 AI 画） |
| 战场背景 | 640×360 |
| 模组图标 | 16×16 或 24×24 |
| 攻击特效 | 24×24 ~ 48×48 |

### ⚠️ 战场背景必须是**等距正交**，不能是透视

2026-10-01 实测发现：AI 生成的这张 `bg_plaza.png` 画得不错，但它是**透视视角**
（地面铺装线向消失点收敛），而我们的网格是**纯正交 2:1 等距投影**（平行线永远平行）。
两者叠在一起有轻微违和——网格"浮"在地面上，没有真正贴着铺装。

- **原型阶段**：可以忍，这是占位图；
- **正式资源**：**战场背景必须按等距正交画**——地面铺装线走向要和 `iso_to_screen()` 的
  两条轴（斜率 ±0.5）平行。否则网格永远贴不上去，只能靠把网格做得很淡来遮丑。

> 这一条也是"箱庭与战斗共用等距"的**隐性成本**：背景不能按好看的透视画，得按能对上的正交画。

## 七、⚠️ 等距带来的结构性改动（不是换贴图）

**这是选等距的真正代价，必须先知道。**

现在的战斗界面是**"卡片列表"布局**：用 `VBoxContainer` / `HBoxContainer` 排两排卡片，方块在两点之间直线飞行。
等距要求的是**真正的空间场景**：地面菱形格、角色站在格子上、镜头固定。

| 层 | 影响 |
| --- | --- |
| `features/battle/`（战斗逻辑） | ✅ **零改动**。它不依赖场景树，这正是当初分层的意义 |
| `tests/`（自动化测试） | ✅ **零改动** |
| `playgrounds/battle_screen.gd`（表现层） | ⚠️ **要重写** |

表现层需要新增/改写的东西：

1. **等距坐标转换**：格坐标 → 屏幕坐标（`iso_to_screen()`），以及它的逆运算（用于点击选人）；
2. **单位从 UI 卡片变成场景精灵**：`ColorRect` + `Label` → `Sprite2D` / `Node2D`；
3. **站位设计**：3v3 在等距场地上怎么摆（我方一片、敌方一片，还是交错）；
   ⚠️ 硬约束：**同排相邻至少隔 2 格**（64px），否则 64px 宽的精灵互相压 50%（见 §一）。
4. **血条 / 资源 / 名字**：不再是卡片的一部分，要改成跟随精灵的浮层；
5. **攻击演出方向**：不再是垂直下落，而是沿等距方向斜向飞行；
6. **层级排序**：等距必须按 y 坐标排序遮挡，否则角色会互相盖错。

**建议的推进顺序**：先把表现层改成"等距空场景 + 色块小人"跑通（**不依赖任何美术**），
确认站位、点击选人、层级排序都对，**再往里塞像素资源**。
否则会出现"美术给了但摆不进去"的返工。

## 九、⚠️ 遗留：AI 生成 vs 真像素画（未解决）

这是当前**唯一没有答案**的规格问题，需要在正式投入美术前拍板。

| | AI 生成（当前做法） | 真像素画 |
| --- | --- | --- |
| 源图 | 1024px 插画，缩到 64×96 | 直接在 32×48 / 64×96 画布上逐像素画 |
| 观感 | "高分辨率缩略图"——**不是像素画**，放大后是模糊的块，不是硬边像素 | 真正的硬边像素，风格统一、放大后干净 |
| 尺寸 | **必须 ≥64×96** 才可辨识 | 32×48 就够（画家控制了细节密度） |
| 成本 | 低，可批量出 | 高，需要像素画师 |
| 一致性 | 每次生成风格会飘，需要人工筛 | 完全可控 |

**为什么现在用 AI**：这一阶段的目的是「**看得出这是个人、分得清是谁**」，
AI 图已经达到这个标准，而且能立刻拿到、立刻验证规格。

**什么时候必须换**：当要追求"**看起来是像素游戏**"时。
现在的 `hero_wolf/idle.png` 缩到 64×96 后**可辨识但不是像素风**——
边缘是抗锯齿的柔和过渡，和真正的像素画放在一起会明显不是一个体系。

> **待拍板**：正式资源走哪条路？
> - 走 AI → 尺寸维持 64×96，接受"高分辨率缩略"观感；
> - 走真像素画 → 尺寸可以降回 32×48，但要找到能画的人/工具；
> - 折中 → 用像素风模型重出（仍是 AI，但输出就是像素画），尺寸待实测。
