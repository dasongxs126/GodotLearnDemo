# GDScript 注释规范

用于约束项目内 GDScript（`.gd`）代码的注释编写与维护。Godot 4 的文档注释使用 `## ` 开头的 Document Comment（等价于 Javadoc/KDoc），由 `##` 后跟一个空格；文档块内部使用 Markdown 与 `@param` / `@return` / `@deprecated` 等 GDScript 标签。普通行注释使用 `#`。专有名词、协议名、类型名和关键字保留英文原文。

`addons/` 下第三方插件保持上游注释风格，不作为本规范的整改对象，也不要顺手改写。

## 一、强制规则

### 1. 脚本、成员与函数注释

- 所有脚本（含 `class_name` 声明的类）、`@export` 与类成员变量、常量、信号、枚举、函数必须使用 Document Comment，格式为 `## ...`，不得使用 `# ...` 代替。
- 注释必须准确说明职责和业务含义。函数注释应根据实际签名和行为说明参数、返回值、副作用与必要的调用注意事项。
- 生成或修改任何函数时，必须同步生成或更新符合本规范的中文文档注释，禁止只修改代码而不维护注释。
- 注释应能够被 Godot 编辑器悬浮提示、脚本概述和 `classdb`/文档工具正确识别；`##` 紧贴文字（无空格）或写成 `#` 都不算文档注释。

函数注释示例：

```gdscript
## 根据用户 ID 查询用户资料。
##
## 只读取本地存档，不触发网络请求。
##
## @param user_id 用户 ID
## @return 用户资料；用户不存在时返回 [code]null[/code]
func get_user_profile(user_id: String) -> UserProfile:
	...
```

多行文档块内换行使用一个 `##` 空注释行分隔段落，行内标记使用 Godot 的 BBCode 风格（`[code]`、`[b]`、`[url]`）。

### 2. 虚方法、抽象契约与接口方法

- 供子类重写的虚方法、`class_name` 抽象基类中的契约方法，一律必须有文档注释。GDScript 没有 `abstract` 关键字，契约通过基类中 `assert(false, "...")` 或 `push_error()` 表达。
- 除参数、返回值和副作用说明外，必须明确说明方法做什么、实现什么功能。
- 对子类或实现方的行为要求、执行时机（`_ready` / `_physics_process` / 信号回调）、状态变化、调用顺序和其他注意事项，必须一并说明。

```gdscript
## 提交当前编辑内容并通知监听方提交结果。
##
## 实现方必须保证 [signal submitted] 只触发一次，且在主线程通知监听方。
## 调用方必须在 [member is_editing] 为 [code]true[/code] 时调用，否则视为错误。
##
## @param content 待提交的编辑内容
func submit(content: EditContent) -> void:
	push_error("Submitter.submit 必须由子类实现。")
```

### 3. 脚本的作者和创建日期

- 所有脚本都必须在文件顶部的文档注释中写明作者和创建日期。
- 创建日期统一使用 `yyyy-MM-dd` 格式。
- 作者取当前提交者姓名或用户名；由 Agent 生成的脚本统一标注实际驱动者，不得虚构他人姓名。
- 位置固定：`@tool` 等注解之后，`extends` / `class_name` 之前（Godot 只把紧贴声明之前的注释块识别为声明文档，因此作者块与类说明之间不留空行）。

```gdscript
@tool
extends Node

## 用户资料页状态管理器。
##
## 负责缓存资料、驱动 UI 刷新、在存档切换时重置状态。
##
## @author kled
## @date 2025/09/10
class_name UserProfileManager
```

### 4. 函数内部注释

- 函数内部的单行注释必须在被注释语句上方另起一行，使用 `# ...`，不得写在语句行尾。
- 函数内部的多行注释使用 `#` 连续多行；Godot 的 `#` 注释不能嵌套，也不支持块注释跨越字符串语句，禁止使用 `/* */`。
- 注释缩进必须与对应代码保持对齐（Tab 缩进环境下同样使用 Tab 对齐）。

```gdscript
	# 过滤已失效的数据，避免进入后续聚合流程。
	var valid_items: Array[Item] = _filter_valid_items(items)

	# 服务端可能返回重复记录：
	# 1. 优先保留更新时间较新的记录；
	# 2. 更新时间相同时保留首次出现的记录。
	var distinct_items: Array[Item] = _remove_duplicates(valid_items)
```

### 5. 枚举与导出成员注释

- 所有枚举常量必须使用文档注释说明对应数据项的业务含义和用途；`enum` 整体也需说明使用场景。
- 所有 `@export` 变量必须注释说明其在编辑器中代表什么、合法取值范围、修改后是否需要在运行时生效。

```gdscript
## 订单流转状态。
enum OrderStatus {
	## 订单已创建，等待用户付款。
	PENDING_PAYMENT,
	## 订单已付款，等待商家发货。
	PAID,
}

## 角色每帧最大水平移动速度，单位：像素/秒。取值范围 [code]1 ~ 2000[/code]。
@export_range(1, 2000) var max_speed: float = 300.0
```

## 二、推荐规则

### 1. 优先使用准确的中文注释

- 无法用准确英文表达时，优先使用中文说明清楚，避免含义模糊的英文注释。
- 专有名词和关键字保留英文原文，例如 `TCP 连接超时`、`physics_process`、`CharacterBody3D`，不必展开为冗长的中文全称。

### 2. 代码与注释同步更新

- 修改代码时必须检查并同步更新相关注释，重点核对参数、返回值、副作用、信号发射时机和核心逻辑。
- 发现注释与实现不一致时，以当前业务和实现为依据修正注释，不得保留误导性说明。
- 改动 `@export`、`class_name`、信号签名后，除代码外必须同步检查场景（`.tscn`）中的赋值与连接，并更新对应注释。

### 3. 删除未使用代码

- 脚本中未使用的成员变量、函数、内部类、`@export` 与常量应当删除。
- 函数中未使用的参数声明和局部变量应当删除；确实需要保留占位参数时使用 `_` 前缀并在注释中说明。
- 因信号连接、场景挂载、引擎回调或存档兼容性而暂时无法删除时，应在注释中准确说明保留原因。

## 三、参考规则

### 1. 谨慎注释代码

- 不要简单地将无用代码注释掉；确认无用后应直接删除，历史实现通过代码仓库查询。
- 确需暂时保留被注释代码时，必须在其上方说明保留原因、恢复条件、责任人和预计处理时间。

### 2. 注释应表达设计与业务

- 注释应准确反映设计思想、代码逻辑和业务含义，使维护者能够快速理解代码背后的约束与目的。
- 对复杂逻辑应说明“为什么这样做”和关键限制（帧序依赖、`await` 边界、物理回调重入限制等），避免只把代码逐句翻译成自然语言。

### 3. 保持精简准确

- 优先通过清晰的命名和代码结构实现自解释，注释只补充代码本身无法清楚表达的信息。
- 避免过多、重复或失效的注释，降低代码修改时的维护负担。

反例：

```gdscript
	# 把大象放进冰箱
	put(elephant, fridge)
```

函数名和变量名已经准确表达行为，不需要重复注释。

### 4. 特殊注释标记

- `TODO` 和 `FIXME` 必须注明标记人、标记日期；可以确定处理时间时，还必须注明预计处理时间。
- 日期统一使用 `yyyy-MM-dd` 格式，并通过日常扫描及时处理和清理。
- `TODO` 表示需要实现但当前尚未实现的功能，按本项目约定仅写在脚本、函数、成员和枚举的文档注释（`##`）中，方便编辑器概述与检索。
- `FIXME` 表示当前代码存在错误或无法正常工作，必须及时修正，允许出现在函数内部的 `#` 注释中。

```gdscript
## TODO(zhangsan, 2025/09/10, 预计 2025/09/17)：补充离线缓存恢复能力。
func restore_cache() -> void:
	# FIXME(zhangsan, 2025/09/10, 预计 2025/09/12)：空缓存时会触发空指针异常。
	cache.restore()
```

无法确定预计处理时间时：

```gdscript
## TODO(zhangsan, 2025/09/10)：等待服务端提供批量查询接口后实现。
```

## 四、场景与资源注释

- `.tscn`、`.tres` 中的 `metadata/` 键与节点 `editor_description` 用于说明节点用途、脚本挂载约定；使用 MCP 的 `modify_node_property` 写入，不要手改二进制场景字段。
- `project.godot` 只在有明确理由时手工修改，改动后在提交信息中说明原因；`[autoload]`、`[input]`、`[layer_names]` 的新增项必须能对应到代码中的常量或 Autoload 脚本注释。
- Shader（`.gdshader`）中的 uniform 与自定义函数需要注释说明视觉用途、单位与取值范围。

## 五、生成与修改代码检查清单

生成或修改 GDScript 代码后，至少检查以下内容：

- 脚本、成员、常量、信号、枚举、函数是否使用 `## ` 文档注释，而不是 `#`。
- 新增或修改的函数是否具有准确的中文文档注释，`@param`、`@return` 是否与签名及实现一致。
- 虚方法与基类契约方法是否说明功能、实现要求与调用时机。
- 脚本头部文档注释是否包含 `@author` 和符合 `yyyy-MM-dd` 格式的 `@date`。
- 每个枚举常量与 `@export` 变量是否说明业务用途、取值范围。
- 函数内部注释的位置、格式和缩进是否正确，是否存在误用 `/* */`。
- `TODO`、`FIXME` 是否包含标记人和标记日期，并在可确定时包含预计处理时间。
- 是否存在失效注释、被无理由注释掉的代码或可以删除的未使用代码。
- 修改 `class_name`、信号、`@export` 后是否跑过 `godot --headless --import` 与 `godot_validate_script` 确认场景引用未断。
